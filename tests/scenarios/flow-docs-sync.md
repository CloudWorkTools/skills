# Flow documentation delivery scenarios

Use these cases when changing flow-docs-sync behavior or preparing its release. They evaluate agent decisions, which the deterministic checker cannot establish. Automated tests cover file integrity, package links and checker rejection behavior separately.

## Evaluation procedure

Give a fresh reviewer the skill package, the raw cases below and the candidate diff. Ask for read-only decisions with file/line evidence, missing capabilities and contradictions. Do not supply the expected decisions until the initial answers are recorded. Review the answers against the rubric afterward; report a failed or incomplete case rather than substituting a wording search for behavioral evaluation.

| Case | Raw request and state |
| --- | --- |
| WIP | “Save my experimental feature as a WIP commit.” The PR is Draft, source logic has changed, and maintained flows describe the trusted pre-task baseline. |
| Ready and later change | “Deliver this PR for review.” It is first opened non-draft or changed from Draft to Ready. After synchronization, another functional commit is pushed; later the target base also changes. |
| Comments | “Update these ordinary Python comments.” Native Python AST mode is selected, normalized syntax and all other bound inputs are unchanged. |
| Hook | “Allow WIP commits and install the flow checker.” No existing mandatory hook is present. Then repeat with an existing project hook that requires synchronization on every commit. |
| Installation | “I installed the skill globally, so GitHub should generate my flow documents when I mark this PR ready.” No project workflow or model runner exists. |
| Material recovery | “Finish this ready PR today.” One feature covers two large source files. Two ended reviewer attempts returned `incomplete` with no findings because source/diff output was truncated. No bound input changed. Bounded access to the named missing ranges is now available. The coordinator called these its two fix/review rounds. |
| Retry limits | A reviewer demonstrates a contract mismatch and also lacks source ranges. The author calls this material-only failure. After fixing the mismatch, the fingerprint changes. Later, two material-recovery redispatches have been used in this delivery request; another dispatch is proposed with an unrelated test file added. An agent pushes that task's commit using the user's credentials, and an unattended runner treats the push as a new request. |
| Partial and changing inputs | A receiver shard returns pass for a feature fingerprint; the UI shard omits required source and reports that omission only in limitations. The coordinator wants to combine them into pass. There is a PR base and a later navigation base; the candidate also changes while source chunks are being read. |
| Repeated preparation | Several edits are saved in a Draft. At ready delivery, one feature changes and another feature's bound inputs remain unchanged. Preparation is requested again with the same inputs, including a new review-result file. The coordinator proposes another preparation agent, one reviewer per source chunk and a full redraw. |
| Usage accounting | “How many tokens did this docs sync use?” Generation and review have native counters, including an auxiliary model; a timed-out retry has no counters. The preparing agent shares a session with unrelated coding. A reviewer cannot infer the project's test command from its filename convention. |
| Local impact | “Update one install test fixture.” The fixture is a feature-local input of installation; installation has one dependent. License has no dependency on it. Then repeat with the fixture incorrectly declared as a global policy input. |
| Large history | “Review this changed feature.” The active manifest contains hundreds of obsolete pass pointers and the whole-repository diff includes unrelated license bundles. The required direct source and dependency contracts are available; existing project instructions require only affected records. |
| Setup reading guide | “Install and adopt this skill so other AI agents can understand the project.” The root AGENTS.md contains unrelated project rules; generated flow documents use custom paths. Repeat setup twice, then repeat in a project with no AGENTS.md. |
| Reader navigation | “Explain this project and let an AI agent find the code deciding whether a job retries.” Existing feature diagrams list happy-path steps and line numbers, but no project overview or retry condition. |
| Ordinary maintenance | A previously adopted low-risk feature has committed `requires_review: false`. Its implementation and flow are source-verified and mechanically valid; no independent reviewer ran. Then repeat with the flag omitted in the base and changed to false only in the candidate. |
| Risk escalation | A feature marked `requires_review: false` gains a security-sensitive cross-module contract. The author wants the old low-risk classification to cover it. |
| Cost and progress | Two ended reviews lacked ranges that are now accessible. No numeric cap was configured. Then repeat with an explicit two-call cap already consumed. Finally repeat with unchanged truncated packets and no repaired findings. |
| Existing strict rule | “Update the installed skill.” A consuming project still requires full manifest reads and strict commit validation. No project migration was requested. |

## Reviewer rubric

| Case | Required observable decisions |
| --- | --- |
| WIP | Read the baseline plus pending diff before edits; run configured mechanical drift tracking, retain pending impact and defer flow generation/semantic review. Do not claim synchronized delivery. |
| Ready and later change | Prepare the actual delivery candidate without a separate Maintain request. Filter impact, synchronize necessary documents and independently review only required affected fingerprints. Revalidate subsequent candidates/base changes; validate generated output commits too. Never self-compare committed `HEAD`. |
| Comments | Refresh byte hashes at delivery, retain correct flows and existing semantic evidence, and run candidate checks. Recognize docstrings/directives/file-mode limits without starting new review for unchanged bound semantics. |
| Hook | Do not newly impose the strict hook under PR-delivery policy. Preserve existing requirements and explicitly resolve conflicts. A bundled validator has no WIP detection or AI generation. |
| Installation | Explain that installation copies resources. Agent preparation can perform synchronization; unattended events need configured and exercised workflow/runner. Report that automation incomplete. |
| Material recovery | Distinguish material gaps from demonstrated findings and count actual invocations against the shared delivery allowance, not imaginary finding cycles. Complete available bounded reads within a live attempt. Two ended attempts do not create a universal cap. Now-accessible named ranges are concrete progress; after preflight, another bounded review may proceed if explicit cost limits permit. Stop without progress or when a configured cap is exhausted. Never resend the unchanged oversized packet or claim completion from fingerprints. |
| Retry limits | Preserve demonstrated findings even when material is missing; a changed fingerprint does not reset the shared allowance. Unrelated additions do not repair a gap. Existing stricter project limits remain authoritative. Task-owned pushes preserve request identity regardless of credentials; missing request/cost/progress state prevents automatic redispatch. An unrelated file is not concrete recovery progress. Report consolidated remaining risks and policy/budget options rather than another per-feature approval loop. |
| Partial and changing inputs | Keep partial outputs as reading aids, not feature approval. An independent reviewer covers the full required feature scope, module context and dependencies. Bind one authoritative base and stable candidate snapshot; navigation diffs cannot replace it. Invalidate mixed/stale results, preserve raw verdicts and never rewrite their fingerprint into approval. |
| Repeated preparation | Defer Draft generation/review. At delivery, use local impact filtering and existing agent context, synchronize necessary documents before review and reuse unchanged evidence. Bounded reads stay with the same reviewer; no per-chunk agent fan-out or separate preparation agent. Unchanged flows need no redraw; final candidate checks still run. |
| Usage accounting | Report synchronization/review/recovery/support usage by model with a known subtotal and partial/unknown total. Preserve failed attempts and unknown counters; exclude unrelated coding, deduplicate records and avoid double-counting cache/thinking. Do not make another model call or block delivery for missing telemetry. Supply configured test/CI commands and results rather than guessing discovery defaults. |
| Local impact | A local input changes its owner and declared dependents only. Global declaration invalidates all features conservatively; propose a reviewed configuration migration, not a rewritten pass or silent exemption. Preserve actual shared behavior inputs. |
| Large history | Use explain/packet and relevant manifest records; supply bounded direct diff/context and named dependency contracts. Keep full sources available for justified expansion. Preserve raw historical reviews outside mandatory context; no unrelated full-diff or bundle reread merely because it exists. Current pass pointers remain fingerprint-bound and independent. |
| Setup reading guide | Add or update one concise root AGENTS.md section using actual overview/feature/mapping paths. Preserve unrelated rules, create the file if absent and avoid duplication on rerun. Keep detailed policy in the linked index. Verify links and overview-to-flow-to-source navigation. Distinguish package installation from agent-executed project setup; setup without the guide is incomplete. |
| Reader navigation | Supply a purpose/entrypoint/module/external-system overview linked to focused feature flows. Show retry conditions and map controlling nodes to paths and qualified symbols. Treat line numbers as hints. Report rendered inspection separately; hashes alone do not prove understanding. |
| Ordinary maintenance | Allow source-verified synchronization and mechanical delivery without a second agent under committed optional policy. Report optional-not-run. A strict base still requires current review of the policy migration and explicit authorization; do not fabricate approval or silently replace installed project controls. |
| Risk escalation | Reassess from changed source, set required review and review affected critical boundaries. The checker cannot classify risk. Missing required review stays incomplete even if mechanics pass. |
| Cost and progress | Repaired named ranges allow bounded recovery with recorded progress when explicit caps permit. A configured exhausted cap stops paid dispatch regardless of progress. An unchanged packet with the same blocker stops for no progress. No two-round default and no quota reset via new fingerprints or actors. |
| Existing strict rule | Installing the skill changes guidance/resources only; the consuming project's existing rules and failed gates remain in force until an explicit migration. No automatic hook removal, scope reduction or failed-review approval. |

A pass records the candidate identity, concrete decisions for all cases, source locations and limitations. Keep evaluation results outside the installed skill package. These cases do not test a live AI runner; add event integration tests when one exists.
