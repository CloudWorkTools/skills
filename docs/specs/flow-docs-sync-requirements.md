# Flow-docs-sync 需求與驗收

| 項目 | 說明 |
| --- | --- |
| 狀態 | 已確認方向的需求整理，作為後續驗收基準，不代表所有整合能力已完成。 |
| 使用者 | 需要理解專案的人類，以及需要定位程式碼與修改影響的 AI agent。 |
| 範圍 | 專案流程導覽、來源映射、版本同步、精簡閱讀指南與審查成本控制。 |
| 維護責任 | Skill 維護者負責規則與 checker；導入 agent 負責專案設定與驗證；專案維護者決定本地政策。 |

## 1. 目的

人類能從流程圖理解專案的用途與主要運作方式。AI agent 能從總覽找到功能流程，再定位入口、判斷條件與控制邏輯。程式變動後，系統能指出需要重新確認的文件，並在交付前完成受影響部分的同步。

審查是依風險與專案政策啟用的品質措施。一般文件同步不應因通用的兩輪審查上限而中止。

## 2. 術語與範圍

- 安裝是把 skill 資源放到可使用的位置。專案導入是由 agent 建立文件、映射、閱讀指南與所選整合設定。
- 受影響功能是來源、文件、映射、政策或已宣告依賴的指紋發生變動的功能。
- 文件同步是 agent 已依目前來源確認描述，必要修改已完成；機械檢查通過本身不代表語意正確。
- 獨立審查是作者以外的 reviewer，針對明確版本與完整必要範圍給出結果。
- 立即追蹤是設定好的觸發點執行影響檢查並回報結果，不承諾每次存檔即重畫流程圖或呼叫模型。

本次不要求另建背景監控服務、通用 AI runner 或自動依賴推斷系統。專案若要無人值守觸發，必須另外設定並驗證 runner 與事件整合。不得把安裝成功當成自動化已完成。

## 3. 必要產物與閱讀順序

| 編號 | 產物 | 需求與驗收 |
| --- | --- | --- |
| R1 | 專案總覽與索引 | 說明用途、主要入口、核心控制／資料流、模組責任與外部系統。各階段連到功能流程。讀者能依總覽說明一個主要使用情境如何完成。 |
| R2 | 功能流程圖 | 呈現相關條件、分支、結果、副作用及適用的失敗、取消、恢復路徑。讀者能找出一個成功路徑及適用的例外路徑。 |
| R3 | 節點到來源映射 | 受檢節點對應存在的檔案；AST 模式使用有效的限定符號名稱。AI agent 能從決策節點找到實際控制條件，不能只找到同名但無關的函式。行號僅作提示。 |
| R4 | 版本與覆蓋紀錄 | 記錄可信 base、候選版本或快照、受影響功能與指紋。清楚列出未納入範圍及未知依賴，不能把部分覆蓋稱為全專案覆蓋。 |
| R5 | 根目錄 AGENTS.md | 導入 agent 必須新增或原地更新一節精簡閱讀指南。保留其他規則，沒有檔案就建立，重複導入不重複追加。未完成指南不能宣告專案導入完成。 |

R5 只放閱讀入口、定位方式及交付提醒，詳細操作與政策留在索引。實際文字可依專案語言調整，路徑必須指向真實產物。例如：

```markdown
## 流程文件
修改前先讀 [專案總覽](docs/flows/README.md)，再讀相關功能流程與契約。
透過 docs/flow-manifest.json 的節點映射定位檔案與函式；變動或缺漏回查程式碼。
交付前同步受影響流程並執行專案檢查；觸發條件與審查要求見流程索引。
```

驗收需實際跟隨指南完成「總覽、功能流程、控制程式碼」的導覽。連結存在與檔案已載入，不等於 agent 已讀懂內容。

## 4. 觸發與同步行為

| 編號 | 觸發條件 | 必要行為 |
| --- | --- | --- |
| R6 | 初次專案導入 | 建立必要產物與 R5 指南，完成已採用範圍的初次獨立審查，記錄真實覆蓋與整合狀態。 |
| R7 | 開發中、Draft 或 WIP | 依已設定的任務／commit／PR 檢查點追蹤變動並保留待確認清單。檔案 hash 過期回報為待同步，不因此自動啟動獨立審查。 |
| R8 | 任務交付、PR 就緒或明訂的 commit 邊界 | 固定比較版本，依來源確認受影響功能，只更新必要文件，執行 checker 與既有專案檢查。 |
| R9 | PR 後續更新、base／政策／依賴變動 | 重新判定影響與證據有效性，只重做失效部分。受保護的合併檢查必須針對實際候選版本。 |
| R10 | 重複觸發且輸入未變 | 重用仍有效的資料與證據，不重畫圖、不另外呼叫 reviewer；仍完成該候選應有的檢查。 |

專案索引記錄選用邊界、實際命令、hook／workflow 位置與 runner 狀態。未設定的自動觸發必須標示未啟用。保留原有較嚴格規則，不能偷偷新增 WIP 阻擋或移除現行 gate。

僅格式或註解變動，依所選 AST／file 模式判定。AST 可排除支援的外觀差異；file 模式仍按位元組保守判定。新增入口、檔案、符號及依賴不能只刷新 hash，必須補足登錄與映射。

## 5. 同步與審查狀態

R11 要求交付報告分開呈現以下項目，可沿用現有 task／CI 紀錄，不新增一套必要狀態檔。

| 項目 | 可觀察狀態 |
| --- | --- |
| 來源與文件 | 輸入未變、來源已變待確認、已依來源確認並完成必要更新。 |
| 機械檢查 | 通過、失敗、未執行，附候選與實際結果。 |
| 獨立審查 | 必要且通過、必要但未完成、選擇性且未執行；選擇性審查有執行時如實附結果。 |
| 其他驗證 | 視覺、執行期、人類批准及遠端整合各自報告已驗證或未驗證。 |

即使不要求獨立審查，已證明的文件／程式矛盾也不能宣告同步完成。`snapshot` 只刷新完整性資料，不代表來源確認或批准。必要審查未完成時，文件更新仍可交付檢視，但專案要求的合併門檻保持未通過。

## 6. 風險與審查政策

R12 使用功能層級的 `requires_review`。未填視為 `true`，維持既有專案行為。

- 初次導入、重要跨模組契約、安全或資料損失風險，以及專案明訂的情況，需要獨立審查。
- 一般低風險維護在來源確認後，可明確採用 `false`，並記錄判斷依據。
- 功能風險升高時重新判斷並提高要求。Checker 驗證宣告，不負責判斷風險。
- 從嚴格政策改成選擇性審查，需要授權及遷移審查。只有遷移進入可信比較基準後，普通變更才可使用較寬政策；同一 PR 內新增遷移 commit 不會放寬舊 base。

必要審查只讀受影響的直接上下文與相關契約，不因傳遞指紋變動就強制重讀整個專案。審查前先修正語法、映射與已知材料缺漏。

## 7. 額度與停止條件

R13 不設通用的「初審一次加追審一次」上限。有明確額度時，記錄單位、上限與已用量，單位可為模型呼叫、時間或 Token，優先遵守使用者、環境與既有專案限制。

R14 只有已修正具體問題，或已補齊具名缺漏材料，才有理由再次派送。相同阻礙反覆出現而沒有新證據，或明確額度耗盡，就停止自動派送並保留問題。換 reviewer、指紋、帳號或 commit 不重設花費。

無數字上限時明示未設定，不虛構配額。若明訂硬上限卻無法量測或執行，停止付費自動派送並回報。未知用量不算零，也不能拿來宣告成本下降。實際數值與進展控制由執行 agent 或專案 runner 負責。

## 8. 驗收案例

| 編號 | 情境 | 通過條件 |
| --- | --- | --- |
| A1 | 初次導入及重複導入 | 必要產物齊全，指南使用真實路徑且沒有重複節；原有規則保留。 |
| A2 | 人類理解與 agent 定位 | 人類能沿圖說明主要情境；agent 能沿節點定位成功及適用例外分支的控制程式碼。另記視覺驗證結果。 |
| A3 | 一個功能變動 | 指出該功能及已宣告受影響依賴，未受影響功能不被重畫或重審。圖不必改時留下來源確認依據。 |
| A4 | 新增未映射入口或符號 | 檢查指出缺漏；只刷新 hash 不能使其通過。 |
| A5 | 低風險且可信 base 已採選擇性審查 | 機械檢查及來源確認通過後可交付，獨立審查如實記為未執行。 |
| A6 | 嚴格 base 的政策遷移 | 即使候選為 false 或已在 PR 內提交遷移，缺少當前審查仍不通過。 |
| A7 | 兩次截斷後已補足材料 | 未耗盡明確額度時可再審；不被兩輪通用門檻阻擋。 |
| A8 | 無進展或額度耗盡 | 停止自動重試，統整阻礙與成本；不偽造通過，不阻止其他可安全完成的工作。 |
| A9 | 已安裝但未設定 runner | 正確回報自動化未啟用，不聲稱 GitHub 事件已執行產圖。 |

確定性驗證使用 [checker 測試](../../tests/flow_checker_test.py) 與 `npm test`。行為驗證使用 [原始情境與評分規則](../../tests/scenarios/flow-docs-sync.md)，先給獨立 reviewer 原始情境，再比對評分規則。實際專案導入、事件與圖像呈現需另留執行證據。

## 9. 依據、取捨與實作邊界

規則與機械能力以 [skill](../../skills/flow-docs-sync/SKILL.md)、[checker 契約](../../skills/flow-docs-sync/references/enforcement-contract.md) 與 [審查規則](../../skills/flow-docs-sync/references/reviewer-prompt.md) 的目前工作樹為核對來源。政策取捨見 [已確認決策](../decisions/2026-11-13-flow-docs-sync-review-policy.md)。本文件整理預期結果與驗收；欄位與命令細節由原有契約維護。

沿用現有 manifest、checker 與證據紀錄，避免新增平行狀態系統。所有變動都強制獨立審查能增加預設保障，但也增加一般維護的模型工作；完全取消限制則可能無限重試，因此採風險分流、明確額度與無進展停止。

來源映射、hash 與語法檢查不能證明語意理解或畫面可讀。導入 agent 與專案維護者仍須確認風險分類、真實依賴及閱讀結果。尚未驗證的整合能力應列為未驗證，不能從需求文件或測試通過推論已部署。
